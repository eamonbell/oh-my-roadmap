# /roadmap:new

Create a new gated roadmap workflow. Inspect existing code and documentation before drafting. Use the built-in `ask` tool to interview the user until goal, success criteria, audience, constraints, scope, discovery findings, external research needs, open questions, concrete roadmap milestones, milestone substance, and approval state are clear. Use `roadmap_engineer_init` once the roadmap slug and title are known, then use `roadmap_engineer_transition` with `record_discovery` when repo discovery is complete. Before asking for roadmap approval, call `roadmap_engineer_update_roadmap` with the full structured roadmap: goal, success criteria, constraints, non-goals, context, evidence, risks, and at least one concrete milestone outline. After the roadmap is written, dispatch roadmap-milestone-checker to check milestone conflicts, sequencing, and buildable milestone boundaries; record the result with roadmap_engineer_transition operation record_roadmap_milestone_check. If the checker fails, revise with roadmap_engineer_update_roadmap, rerun the checker, and record the new result before asking for approval. Each roadmap milestone must include goal, scope, non-goals, evidence, dependencies, risks, acceptance intent, and verification intent. Each roadmap milestone must group multiple meaningful deliverables or workstreams that belong together; fold one small edit, isolated cleanup, or one narrow task into another milestone instead of giving it a separate milestone gate. Do not create milestone plans, tasks, waves, workers, or ownership during `/roadmap:new`; those belong to `/milestone:plan`.
